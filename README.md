# AnPod

把 Windows 的系统输出音频，通过 **USB 数据线** 或 **同一局域网 / Windows 移动热点**
实时送到 Android 手机的扬声器播放。

**只有 Windows 端有界面。** 手机不需要安装任何 App：AnPod 把一段无界面的 Java
服务载荷推到手机，用 `app_process` 启动它，音频经 ADB Reverse 隧道送到手机的
`AudioTrack`。

> **这不是虚拟声卡。** 手机不会作为一个音频输出设备出现在 Windows 的声音设置里。
> AnPod 采集的是 Windows **当前默认输出端点**（WASAPI Loopback），所以 Windows
> 侧仍然需要一个正常工作的播放设备。见 [§10 边界](#10-边界与不做的事)。

> **无线不等于免授权。** Wi-Fi 模式用的是 Android 11+ 的「无线调试」，需要用户在手机上
> 开启并配对；AnPod 不会绕过 Android 的授权，也不会偷偷打开网络 ADB。

## 1. 它是怎么工作的

```
┌─ Windows ──────────────────────────────────────────────────────┐
│  AnPod.exe (WPF)                                               │
│    ├─ adb.exe  ──►  devices / pair / connect / reverse / push  │
│    └─ audio_capture.dll (WASAPI Loopback)                      │
│            │  PCM16 stereo, 48 kHz                             │
│            ▼                                                   │
│       127.0.0.1:<port>  ◄──── adb reverse 隧道 ────┐           │
└────────────────────────────────────────────────────┼───────────┘
                                     USB 数据线 或  │  Wi-Fi (ADB/TCP)
┌─ Android ──────────────────────────────────────────┼───────────┐
│  app_process com.anpod.server.Main                 │           │
│    └─ LocalSocket(abstract) ──► AudioTrack(MODE_STREAM)        │
└────────────────────────────────────────────────────────────────┘
```

**USB 和 Wi-Fi 只差在 ADB 怎么找到手机。** 一旦设备就绪，两种模式走的是同一条
链路：同一个 `adb reverse`、同一个 `app_process` 载荷、同一份 PCM16 协议。
音频监听从始至终只绑在 `127.0.0.1`，对外不开任何端口——无线模式也没有。

连接顺序（对应代码里的 `ConnectionManager.ConnectCoreAsync`）：

1. 校验设备已授权，且连接方式已确认为 USB 或 Wi-Fi。
2. 清掉 **AnPod 自己** 上一次遗留的 reverse 映射。
3. 初始化 WASAPI loopback（没有默认输出设备就明确报错）。
4. 取一个空闲 loopback 端口。
5. `AudioCapture_Listen` 开始监听（监听失败就换端口重试）。
6. `adb reverse localabstract:anpod_<n> tcp:<port>`。
7. `adb push` 服务载荷到 `/data/local/tmp/anpod_server`。
8. `adb shell app_process` 启动手机端进程。
9. 10 秒内收到握手，且 **connect code 与本次会话令牌一致**，否则拒绝。
10. 开始采集，状态变为 `Streaming`。
11. 静音本机所有活动的播放端点，让声音只从手机出（见 [§6](#6-界面与托盘)）。

音频协议：握手之后，Windows 先发 8 字节小端头
（`uint32 sampleRate` + `uint16 channels` + `uint16 bitsPerSample`），随后是连续的
裸 PCM16 数据，无封装、无压缩。两端都会校验这个头。

### 1.1 无线连接（Wi-Fi）

无线模式下 ADB 用两条命令找手机，**它们用的端口不一样**：

```powershell
adb pair    <ip>:<配对端口>  <6 位配对码>   # 只在首次配对时用，Android 11+
adb connect <ip>:<连接端口>                # 之后每次连接用这个
```

配对端口和连接端口是手机「无线调试」页面上 **两个不同的数字**，混用是这套流程里
最常见的坑。界面上两个按钮分开、两个端口分开标注，就是为了这个。

配对只是换密钥，**不代表音频已经连通**；配对完还要再点「连接」。

**懒得抄端口？点「搜索设备」。** 手机开启无线调试后，会同时在局域网里广播两条 mDNS
服务：`_adb-tls-pairing._tcp`（配对端口）和 `_adb-tls-connect._tcp`（连接端口）。
点「搜索设备」就把它们读回来——结果里只有一台手机时，连接地址会自动填好，不用再去手机
上抄那个数字。同一网络里有两台手机时，AnPod 只认刚配对过的那台（按 IP 比对）；认不出来
就把地址都列出来让你选，绝不替你猜——猜错会把声音送到别人的手机上。

搜索本身依赖 ADB 服务里的 mDNS 组件，而**这个组件有时会僵死，且僵死时看不出来**：
`adb mdns services` 照样立刻返回一个空列表、退出码照样是 0，和「网络里真的没有设备」
长得一模一样。所以 AnPod 先用 `adb mdns check` 确认组件真的在应答，再去读设备列表。
探测不通时直接说「搜索不可用，请手动填地址」，而不是报成「没有搜索到设备」——后者会让
人去查一台本来没问题的手机。这个探测只有重启 ADB 服务才能修好，而 AnPod 不重启别人的
ADB 服务，所以它只报告，不动手。

**USB 和 Wi-Fi 是互斥会话。** 同一时间只有一台手机在播放，也只有一个通道在传音频。
两种方式同时可用时，同一台手机在 `adb devices` 里会出现**两次**（一次是 USB 序列号，
一次是 `ip:端口`）。设备列表**按当前模式过滤**：USB 模式只列 USB 设备，Wi-Fi 模式只列
无线设备，每行仍然标出自己的连接方式（`已连接 USB` / `已连接 Wi-Fi`）。这样列表里永远
不会出现当前模式用不了的设备——以前在 Wi-Fi 模式下还能看到「已连接 USB」的那一行，
既让人以为两种模式是同一个界面，也看不出点下去会作用在哪台设备上。

「自动连接上次设备」同样遵守当前模式：记下来的序列号如果属于另一种连接方式（切换模式后
通常就是这种情况），就不会自动连接，改由用户手动选。连接方式还没确认的设备（`连接方式待确认`）
在两种模式下都会列出来——它不属于任何一种，藏起来只会让列表变空，反而看不出手机其实插着。

**掉线恢复。** 手机会因为息屏、切网、无线调试被关掉而从 `adb devices` 里整个消失——
光靠重新扫描永远等不到它回来，所以 AnPod 会先用 `adb connect` 把它拉回来，再重新扫描。
这条路径只在「自动连接上次设备」和「无线掉线后自动重连」都打开、且上次用的是 Wi-Fi
时才走，并且有次数上限。IP 或端口变了就重新填一次，AnPod 不会无限重试旧地址。

### 「连接」和「从手机播放」是两件事

界面把它们做成了两个独立控件，因为它们的生命周期本来就不同：

* **连接手机** 建立的是会话——reverse 隧道、手机上的 `app_process` 载荷、握手。
* **从手机播放声音** 只决定要不要把音频送过去。

关掉开关**不会**断开手机：`AudioCapture_SetStreamingEnabled(0)` 让采集线程改为发送
静音，socket 保持打开，手机端的 `AudioTrack` 也就活着。所以再打开时是瞬时的，不会
重新握手，也不会重新推送载荷。

之所以发静音而不是直接停掉采集，是因为 socket 就是会话本身：关掉它会让手机端
`read()` 返回 -1 并退出进程，那样每次静音/取消静音都要付一次完整重连的代价。

采集线程在暂停期间仍然正常排空并释放 WASAPI 缓冲区，所以音频引擎不会卡住，
恢复时也没有断层。

## 2. 目录结构

```
AnPod/
├── src/AnPod.Core/            纯逻辑：模型、ADB 输出解析、配置序列化（无 WPF 依赖）
├── src/AnPod.Desktop/         WPF 应用：服务、状态机、界面、托盘
│   ├── Services/AdbRunner.cs            ADB 命令封装（退出码 / 超时 / 取消）
│   ├── Services/DeviceDiscoveryService  按需读取设备列表（无常驻轮询）
│   ├── Services/ConnectionManager       唯一状态机
│   ├── Services/WirelessAdbService      adb pair / connect / disconnect
│   ├── Services/NativeAudioCapture      DLL 互操作
│   ├── Services/PlaybackEndpointMuter   会话期间静音本机播放端点
│   ├── Services/AndroidProcessSession   app_process 长生命周期管理
│   ├── Services/{FileLogger,SettingsService,TrayService}.cs
│   └── ViewModels/MainViewModel.cs
├── src/AnPod.Native/          C++ WASAPI 采集 DLL（含 audio_capture.h）
├── src/AnPod.AndroidServer/   Android 无界面播放服务（Java）
├── tests/AnPod.Core.Tests/    断言式自检，无第三方测试框架
├── tools/CaptureProbe/        硬件诊断探针（静音 / 采集实测，不在解决方案里）
├── tools/SessionProbe/        会话探针：验证「关声音不掉线」（需要真机）
├── tools/UiSnapshot/          把窗口渲染成 PNG，用于无人值守地检查版式
├── packaging/                 构建与打包脚本
├── deps/                      运行时依赖（不入库，见 deps/README.md）
├── upstream/                  上游 commit、许可证、修改清单
└── LICENSES/                  许可证全文
```

`tools/` 下的三个探针都**刻意不进 `AnPod.sln`**：它们是诊断/开发工具，不是产品的一部分。

## 3. 环境要求

| 组件 | 要求 |
|---|---|
| 操作系统 | Windows 10 / 11 **x64** |
| .NET | .NET 8 SDK（编译）/ .NET 8 Desktop Runtime（运行） |
| 原生 DLL | Visual Studio 2022 C++ 工具链 + CMake 3.20+ |
| Android 载荷 | JDK 17+ + Gradle 8.x（或 Android Studio） |
| ADB | Android SDK Platform-Tools |
| 手机 | Android 6.0+，USB 模式需开启 USB 调试；无线模式需 **Android 11+** 且开启无线调试 |
| 网络（仅无线） | 手机与电脑在同一可互访网络，或手机加入 Windows 移动热点 |

首版只支持 x64。没有 x86 / ARM64 构建。

## 4. 编译

### 4.1 Windows 应用

```powershell
dotnet build AnPod.sln -c Release
dotnet run --project tests/AnPod.Core.Tests      # 纯逻辑自检
```

### 4.2 原生采集 DLL

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build-native.ps1
# 产物：deps/audio_capture.dll（x64）
```

### 4.3 Android 服务载荷

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build-android.ps1
# 产物：deps/server
```

`deps/server` 是一个 APK，但 **不用于安装**。它被 `app_process` 当作 classpath
上的 zip 来加载其中的 `classes.dex`。构建完请确认：

```bash
unzip -l deps/server | grep classes.dex
```

### 4.4 打便携包

```powershell
powershell -ExecutionPolicy Bypass -File packaging\publish.ps1
# 产物：artifacts/AnPod-1.0.0-win-x64.zip
```

`deps/` 里缺文件时只会告警，不会中断构建——程序仍能启动，并在界面和日志里说明
缺的是哪一块。

## 5. 首次连接手机

### 5.1 USB 数据线

1. 在手机上：**设置 → 关于手机 → 连续点击「版本号」7 次** 开启开发者选项。
2. **开发者选项 → USB 调试** 打开。
3. 用 **支持数据传输** 的 USB 线连接电脑。
4. 手机弹出「允许 USB 调试吗？」时，勾选「一律允许」并确定。
5. AnPod 状态变为「已就绪」后点 **连接手机**。

AnPod **不会**、也不应该绕过这个授权步骤。

### 5.2 Wi-Fi 无线（Android 11+）

先在 AnPod 顶部把连接方式切到 **Wi-Fi 无线**，然后：

1. 手机上：**开发者选项 → 无线调试** 打开。
2. 点 **使用配对码配对设备**。手机弹出两个东西：
   * `IP 地址和端口` —— 这是 **配对端口**；
   * `Wi-Fi 配对码` —— 6 位数字。
3. 把上面的 `IP:端口` 和 6 位配对码填进 AnPod 的 **手机地址** 和 **配对码**，点 **配对**。
   这一步的地址要填 **配对端口**。配对码只在这一次 `adb pair` 里用，用完 AnPod 就把它从内存里
   清掉，也从不写进配置或日志。
4. **连接地址不用自己抄。** 配对成功后 AnPod 会自动搜一次局域网，把 **连接端口** 直接填进
   **手机地址**——因为同一个地址框在「配对」时是配对端口、在「连接」时必须是连接端口，
   两个数字不一样，这是最容易错的一步。想手动重搜就点 **手机地址** 右边的 **搜索设备**。
5. 点 **连接**。手机出现在设备列表里（状态显示 `已连接 Wi-Fi`）后，点 **连接手机**。

卡住时点 **连接帮助**：它会弹出一个独立的小窗口，按「先查什么、再查什么」的顺序列了 6 条
最常见的原因（配对端口当连接端口用、不在同一网络、公共 Wi-Fi 的客户端隔离、需要重新配对、
息屏被省电策略掐掉、以及最后的「改用 USB」）。做成弹窗而不是嵌在界面里，是因为它很长、
只在出错时才需要，常驻会把真正要点的按钮挤下去。

**用 Windows 移动热点：** 先在 Windows **设置 → 网络和 Internet → 移动热点** 打开热点，
让手机加入，然后按上面同样的步骤做。AnPod 只提供跳转入口和指引，**不会** 替你改系统网络设置。

> 热点能否开启取决于电脑的无线网卡和驱动。没有合适的无线网卡时这个场景不可用，
> AnPod 无法绕过这一点。

**Android 10 及以下** 没有配对码式无线调试。AnPod 不提供 `adb tcpip` 引导流程——
请继续用 USB。

## 6. 界面与托盘

```
AnPod                          [设置]
────────────────────────────────────
[   USB 连接   │   Wi-Fi 无线   ]    ← 连接方式

（Wi-Fi 模式下展开）
① 手机上开启「开发者选项 → 无线调试」
手机地址  IP:端口                        搜索设备   ← 自动填连接端口
┌──────────────────────────────────┐
└──────────────────────────────────┘
配对时填「配对端口」，连接时填「连接端口」——两个端口不一样。
配对码  6 位数字
┌──────────────────────────────────┐
└──────────────────────────────────┘
[   配对   ]  [   连接   ]
☑ 无线掉线后自动重连
连接帮助                断开无线连接   ← 「连接帮助」弹出独立窗口

手机设备                     刷新
┌──────────────────────────────────┐
│ ● vivo V2243A        已连接 USB  │  ← 选一台设备
│ ● Pixel 7            等待授权    │
└──────────────────────────────────┘

● 正在播放（已静音本机扬声器）

[          断开连接          ]        ← 会话

从手机播放声音              [ ●——]    ← 音频
声音从手机播放

☑ 自动连接上次设备
☑ 关闭窗口时最小化到托盘

[查看日志]                    v1.0
```

界面只有两个动作控件，因为它们控制的是两件不同的事：

**① 连接手机 / 断开连接** —— 建立或拆除会话。

**② 从手机播放声音** —— 只决定声音走哪边。关掉它 **不会** 断开手机：状态变成
`已连接，声音从电脑播放`，按钮仍是「断开连接」，reverse 隧道和手机上的载荷都还在。
再打开是瞬时的。

* 连接中 / 重连中开关保持打开状态，不会在握手期间闪回。
* 开关旁边的文字始终说明声音从哪边出——颜色和滑块位置都只是辅助。
* 没有会话时开关置灰（而不是隐藏），这样插上手机时版式不会跳动。

**连接方式切换** 只决定窗口显示哪一套控件。切到 Wi-Fi **不会** 自动执行
`adb pair` 或 `adb connect`——网络 ADB 只在用户明确点按钮时才动。会话进行中两种方式
都不可切换（要先断开，旧通道按顺序清理）。

**设备列表：** 每行自己说明状态，因为用户需要看到 *他想选的那台* 为什么不能选，
而不只是被高亮的那一台。选中项同时用左侧色条和底色表示，不只靠颜色。两种方式同时
可用时，每行会显示它自己的连接方式（`已连接 USB` / `已连接 Wi-Fi`）。

**刷新是手动的。** 空闲的 AnPod 没什么可盯的，所以它不会定时去跑 `adb devices`；
只有建立了会话才会起一个 2.5 秒的看门狗（那时才真的需要发现拔线或端点变化）。
启动时会扫一次，之后由「刷新」按钮和会话恢复流程按需触发。

**静音本机扬声器：** 播放期间会静音 Windows 上所有活动的播放端点，暂停或结束时按
原样恢复。两条硬规则：

* 只恢复 **AnPod 自己静音过** 的端点。你原本就静音的端点，AnPod 不碰、也不会
  替你打开。
* 如果 AnPod 被强杀（任务管理器）或崩溃，来不及恢复的静音会在 **下次启动时自动
  撤销**，日志里会留下 `A previous AnPod run did not shut down cleanly; restored N
  local playback device(s).`

WASAPI Loopback 采集点在端点静音之前，所以静音本机不会让送到手机的声音变静——
这一点由 `tools/CaptureProbe` 在真机上实测确认（见 [§9](#9-测试)）。

* 关闭窗口默认进托盘；只有托盘菜单的 **退出** 才会真正结束进程并清理资源。
* 托盘菜单：`显示 AnPod` / `连接` 或 `断开连接` / `退出`。已连接但暂停播放时，
  菜单仍然显示「断开连接」——手机还连着。
* 重复启动时，第二个实例只会把已有窗口唤到前台。
* 状态颜色只是辅助，文字永远同时存在。

## 7. 配置与日志

| 位置 | 内容 |
|---|---|
| `%LocalAppData%\AnPod\settings.json` | 配置（原子写入，损坏时回退默认值） |
| `%LocalAppData%\AnPod\logs\anpod-YYYY-MM-DD.log` | 日志，按天滚动，保留 7 天 |
| `%LocalAppData%\AnPod\muted-endpoints.txt` | 本次会话静音了哪些端点；正常退出后自动删除，只在崩溃后残留，用于下次启动自愈 |

```json
{
  "schemaVersion": 1,
  "autoConnectLastDevice": true,
  "lastDeviceId": null,
  "minimizeToTray": true,
  "launchAtLogin": false,
  "preferredTransport": "Usb",
  "autoReconnectWifi": true,
  "lastWirelessEndpoint": null
}
```

`preferredTransport` 只记住窗口显示哪套控件；`lastWirelessEndpoint` 是上次成功连上的
`ip:端口`，用来让重连和下次启动有个起点。**配对码不在里面**，也从不写进日志——
它只在那一次 `adb pair` 的内存里存在。

日志里 **不会** 出现音频数据、ADB 私钥或授权令牌；设备序列号和 IP 会被打码
（`R5***AB` / `***`）。

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 插上手机但列表是空的 | 扫描是手动的：点「刷新」。空闲时 AnPod 不会定时扫描，以免一直空跑 `adb devices` |
| 「未检测到设备」 | 换一根**数据线**（很多线只供电）；装对应厂商的 ADB 驱动；确认已开 USB 调试 |
| 「等待手机授权」 | 手机上点允许。若弹窗没出现，撤销授权后重插：`adb kill-server` 后重连，或开发者选项里「撤销 USB 调试授权」 |
| 「设备暂时离线」 | ADB 还在恢复，AnPod 会有限次重试；也可以拔插一次 |
| 「连接方式待确认」 | ADB 没有报告 `usb:` 信息，也无法确认为网络设备。AnPod 不自动连接这类设备 |
| 「未发现可采集的 Windows 输出设备」 | Windows 侧没有可用的默认播放设备 |
| 「Windows 音频格式暂不支持」 | 设备混音格式不是 16 位 PCM 或 32 位浮点。到声音设置里改默认格式为 16 位 / 48000 Hz |
| 「手机端音频服务启动后立即退出」 | 该 ROM 限制了 `app_process` 或无界面音频输出。AnPod 不做 Root 绕过，会明确报错 |
| 连上但没声音 | 手机媒体音量是否为 0；是否被蓝牙耳机抢占；看日志里有没有 `ANPOD PLAYING` |
| 有杂音 / 断断续续 | 看日志是否频繁出现丢包（消费者落后）；把手机省电策略设为「无限制」 |
| 关掉「从手机播放声音」后手机还连着 | **这是设计如此。** 开关只管声音，会话仍在；想断开请点「断开连接」 |
| 列表里的设备点不动 | 会话进行中不能换设备。先「断开连接」 |
| 电脑整体没声音了 | 正常情况下断开连接就会恢复。若 AnPod 是被强杀/崩溃的，**重新启动一次 AnPod** 即自动恢复；不想启动 AnPod 的话，在 Windows 音量合成器里手动取消静音，或跑 `dotnet run --project tools/CaptureProbe -- unmute` |
| 想边听手机边听电脑 | 播放期间本机端点会被静音。临时想听电脑的声音，关掉「从手机播放声音」即可——手机会保持连接，随时可以再打开 |
| 「ADB 服务不可用」 | 其它工具（Android Studio 等）占用 ADB。AnPod 不会杀全局 server |
| 息屏后中断 | 部分 ROM 的行为，属已知兼容性限制；尽量保持亮屏或把 AnPod 加入白名单 |
| 电脑整体没声音了 | 正常情况下断开连接就会恢复。若 AnPod 是被强杀/崩溃的，**重新启动一次 AnPod** 即自动恢复；不想启动 AnPod 的话，在 Windows 音量合成器里手动取消静音，或跑 `dotnet run --project tools/CaptureProbe -- unmute` |
| 想边听手机边听电脑 | 播放期间本机端点会被静音。临时想听电脑的声音，关掉「从手机播放声音」即可——手机会保持连接，随时可以再打开 |

### 8.1 无线连接专有的问题

| 现象 | 原因与处理 |
|---|---|
| 「配对失败：配对码不正确或已过期」 | 配对弹窗已经关掉或码已过期。在手机上重新点「使用配对码配对设备」，用新码重填 |
| 「连不上配对地址」 | 填的是 **连接端口** 而不是配对端口，或者两台设备不在同一网络。核对「无线调试」页面上那两个端口 |
| 「无法连接到该地址」 | ① 手机与电脑是否在同一网络；② 手机上「无线调试」是否还开着；③ 填的是不是 **连接用** 端口。还没配对过的要先配对 |
| 「地址缺少端口」 | 只填了 IP。要填 `IP:端口`，例如 `192.168.1.23:37001` |
| 点 **搜索设备** 说「没有搜索到无线调试设备」 | 搜索靠手机广播，所以手机上「无线调试」必须是开着的。确认开着，等一两秒再点一次 |
| 「系统的 mDNS 搜索当前不可用 / 没有响应」 | ADB 服务里的发现组件僵死了——这时 `adb mdns services` 仍然会返回一个空列表，看不出异常，所以 AnPod 改用 `adb mdns check` 探测，探到就直接说明原因。**搜索修不好，但手动填地址照样能用**；想恢复搜索，关掉其它占用 adb 的工具后重启电脑 |
| 配对成功但列表里没有设备 | 配对只换密钥，不会建立连接。再点一次 **连接** |
| 手机锁屏一会儿就掉线 | 无线调试在息屏后可能被系统挂起。开启「无线掉线后自动重连」和「自动连接上次设备」；省电策略设为「无限制」 |
| **手机的「无线调试」老是自己关掉** | 见下方「为什么无线调试会自己关掉」 |
| 换了网络就连不上 | 手机 IP 和端口都会变。重新看「无线调试」页面填新地址；必要时点 **断开无线连接** 清掉旧记录再连 |
| 公共 Wi-Fi 怎么都连不上 | 很多公共/企业 Wi-Fi 开了客户端隔离，设备之间不能互相访问。改用手机热点或家庭网络。AnPod **不会** 去关你的防火墙 |
| 想彻底放手 | 点面板里的 **断开无线连接**。它只对 AnPod 自己记下的那个 `IP:端口` 执行 `adb disconnect`，**不会** 执行全局 `adb disconnect`（那会踢掉其它工具正在用的 TCP 设备） |
| 无线连不上，急着用 | 切回 **USB 连接** 模式。USB 模式不依赖网络，也不需要配对 |

### 为什么「无线调试」会自己关掉

这是 Android 的设计，不是 AnPod 或手机的故障。常见的触发：

1. **重启手机** —— 无线调试**不跨重启保留**，每次开机都要重新打开。这是「怎么又关了」的头号原因。
2. **Wi-Fi 断开或切换网络** —— 无线调试依附在 Wi-Fi 上；关掉 Wi-Fi、切到别的网络、或走出热点范围，它就会自动关闭。
3. **长时间没有设备连上** —— 部分机型（国产 ROM 尤其明显）在一段时间没有设备连接后会自动关掉这个开关。
4. **系统省电与后台清理** —— 息屏后系统把 `adbd` 挂起甚至杀掉，表现出来就是「无线调试自己关了」。

能做的：

* 设置 → WLAN → 高级 → **「休眠时保持 WLAN 连接」设为「始终」**。
* 电池设置里**关掉对系统的省电优化**，或把省电模式设为「无限制」。
* **别让手机进入深度休眠**（或插着电用），息屏即断网是掉线的主因。
* 打开 AnPod 的 **「无线掉线后自动重连」** 和 **「自动连接上次设备」**。
* 实在频繁就用 **USB 连接**：不依赖网络，也不会自己关。

**关键一点：配对是一次性的，端口不是。** 无线调试重新打开后**不需要重新配对**——
配对记录保留在手机里，变的只是端口。点 **搜索设备** 会自动读回新端口，也可以照手机
「无线调试」页面上显示的 `IP:端口` 手填。所以「又关了」通常只是多按两下，而不是从头来过。

> 顺带一提：无线调试关着的时候，手机**不会在局域网广播**，所以任何搜索（包括 AnPod 的
> 「搜索设备」）都必然找不到它。搜索失败时先看这个开关，比怀疑网络有用得多。

### 9.2 静音行为实测（`tools/CaptureProbe`）

§6 的「静音本机不会让送到手机的声音变静」是一条只能靠真机验证的结论：
WASAPI Loopback 的采集点到底在端点静音的上游还是下游，Windows 没有文档保证。
`tools/CaptureProbe` 就是为回答这一个问题写的，**刻意不进 `AnPod.sln`**——它是
一次性诊断工具，不是产品的一部分。

```powershell
# 1) 观察端点状态（会话前 / 中 / 后各跑一次，看 muted 与 peak）
dotnet run --project tools/CaptureProbe -- check

# 2) 测量：交替静音/取消静音 12 轮，比较两组
dotnet run --project tools/CaptureProbe

# 3) 兜底恢复：AnPod 被强杀后，手动把端点取消静音
dotnet run --project tools/CaptureProbe -- unmute
```

测量模式会先播一段 440 Hz 正弦，然后交替静音 / 取消静音共 12 个窗口，每个窗口
同时记录 **RMS** 与 **440 Hz 频点幅度**（Goertzel，用来把测试音从机器上其它声音
里分离出来）。之所以交替而不是「先测再静音再测」，是因为真实桌面本来就有别的
声音在放，电平会漂移——顺序前后对比会把漂移算到静音头上，交替则让漂移均摊到
两组。

**实测结果（真机，三轮）：**

| 指标 | 静音 / 不静音 比值 |
|---|---|
| RMS | 1.24× / 1.38× / 1.39× |
| 440 Hz 频点 | 0.93× / 0.92× / 0.69× |

端点静音本身由 `check` 独立确认（`MUTED`，峰值表从 `0.2783` 掉到 `0.0080`）。
关键论据是：如果静音位于 loopback 采集点的**下游**，采集结果会**全零**；实际没有。
所以静音本机扬声器不会让送到手机的声音变静——该功能可做。

### 9.3 会话独立性实测（`tools/SessionProbe`）

「关掉声音不会断开手机」是关于 reverse 隧道、手机上的 `app_process` 载荷和 TCP
socket 三者在暂停期间都要活着才能成立的结论，只能在真机上验证。`SessionProbe`
驱动真实的 `ConnectionManager` 跑完整生命周期，并且**用裸 adb 从外部观察设备**，
这样管理器自身的 bug 不会同时污染测量它的尺子。

```powershell
dotnet run --project tools/SessionProbe
```

它断言（当前真机 **18/18 通过**）：

| 阶段 | 断言 |
|---|---|
| 基线 | 没有 AnPod 的 reverse 映射；没有上一次残留的载荷进程 |
| 连接 | `Streaming`；映射存在；载荷在跑；本机端点已静音 |
| **关掉声音** | `Connected`（不是 `Ready`/`NoDevice`）；**映射仍在**；**载荷仍在**；本机端点已恢复 |
| 再打开 | 回到 `Streaming`；仍然**只有一条**映射、**只有一次**载荷进程（没有重新握手） |
| 断开 | `Ready`；映射清掉；载荷停止；端点恢复 |
| 空闲 8 秒 | 设备发现**一次都没有刷新**（无常驻轮询） |

> 计数载荷进程要同时躲开两个坑：Android 的 `zygote`/`zygote64` 也是以
> `app_process` 启动的；而 `adb shell app_process …` 会额外留下一个
> `sh -c app_process …` 包装进程。探针按命令行是否以 `app_process` 开头来数。

## 10. 边界与不做的事

**v1.1 明确不做：** 无 ADB 授权的任意 Wi-Fi 直连、Wi-Fi UDP/Opus 独立音频协议、
蓝牙、Root、虚拟声卡 / Audio Endpoint 创建、手机端可见 App、麦克风转发、
多台手机同时播放、音频录制、账号、自动更新、遥测、自动管理 Windows 热点。

**几个必须说清楚的点：**

* 手机 **不会** 出现在 Windows 声音设置里。那是 USB Audio Gadget / 驱动类项目，
  与 AnPod 的技术路线不同。
* 无线模式 **不是免授权**：手机仍要开无线调试并配对，AnPod 不绕过 Android 授权，
  也不隐藏地改系统设置。
* AnPod **不会** 自动执行 `adb pair` / `adb connect`，也不会调用 `adb tcpip`——
  网络 ADB 只在用户点按钮之后才动。退出时也不会 `adb kill-server`。
* `adb disconnect` **永远带明确的 `IP:端口`**，从不执行全局 `adb disconnect`
  （那会踢掉其它工具正在用的 TCP 设备）。
* AnPod **只** 删除自己创建的 reverse 映射，从不使用 `reverse --remove-all`。
* 监听端口 **只** 绑在 `127.0.0.1`，不对局域网暴露——无线模式也一样。
* 热点只提供 IP 链路，音频仍走 ADB Reverse。AnPod 不替你开热点，也不关防火墙。
* AnPod 不需要管理员权限。
